## Introdução

Um webhook é uma ferramenta que permite a comunicação entre aplicações, possibilitando
o envio de dados para uma aplicação _A_ imediatamente após a ocorrência de um
evento na aplicação _B_. 

Também chamados de _callbacks_, os webhooks substituem a abordagem chamada _polling_, onde uma 
aplicação fica solicitando de tempos em tempos o status de uma ocorrência. Com o
uso de webhooks, a comunicação entre sistemas diferentes torna-se muito mais simples.

## Eventos disponíveis

| Evento | Quando dispara |
| --- | --- |
| `messages.upsert` | Uma mensagem foi recebida ou enviada pela instância |
| `contacts.preference` | O contato pediu para parar (ou voltou a aceitar) mensagens de marketing, ou o integrador marcou isso pela API. Apenas em conexão oficial. **Assinatura opt-in** |
| `contacts.identity` | O vínculo entre telefone, BSUID e username de um contato mudou. Apenas em conexão oficial. **Assinatura opt-in** |
| `messages.update` | Uma mensagem recebida foi editada ou apagada pelo contato. Apenas em conexão oficial, e só em número em coexistência com o WhatsApp Business. **Assinatura opt-in** |
| `messages.status` | O estado de uma mensagem enviada mudou. Em conexão oficial: enviada, entregue, lida ou falhou. Em conexão não oficial: entregue (dois checks) ou lida (checks azuis) |
| `messages.error` | O envio de uma mensagem falhou em definitivo |
| `connection.update` | A conexão da instância abriu ou fechou |
| `group-participants.update` | Participantes entraram, saíram, foram promovidos ou rebaixados em um grupo. Apenas em conexão não oficial |
| `calls.update` | Uma chamada de voz ou vídeo foi recebida, atendida ou encerrada. Em conexão oficial e não oficial |
| `comments.upsert` | Um comentário foi recebido em um post da conta. Apenas em instância do Instagram |
| `token.expired` | O token do Instagram expirou ou foi revogado, e exige nova autorização |
| `token.refresh.failed` | Uma tentativa de renovar o token do Instagram falhou |
| `webhook.test` | Requisição de teste, enviada uma única vez no cadastro do webhook |

Cada webhook recebe **apenas os eventos que assinou**. A assinatura é a lista
`subscriptions` informada no cadastro.

## Como usar

### Pelo painel

Instâncias → (selecione a instância) → **Webhook** → **Novo Webhook**. O passo a
passo, com as validações e o limite de webhooks por instância, está em
[Webhooks no painel](/painel/webhooks).

### Pela API

Cadastre com `POST /{instanceId}/webhooks`, informando um nome, a URL e os
eventos que você quer receber:

```json
{
  "name": "Integração CRM",
  "url": "https://exemplo.com/webhooks/zapperhub",
  "subscriptions": ["messages.upsert", "messages.error", "connection.update"]
}
```

O uso de **HTTPS é obrigatório**. Antes de criar o cadastro, a ZapperHub envia
uma requisição `POST` de teste (`webhook.test`) para a URL informada: se ela não
responder com sucesso, o webhook não é criado.

Consulte a <a href="http://docs.zapperhub.com/api-reference/webhook">Seção
Webhooks</a> na documentação de referência da API para as rotas de listagem,
atualização e exclusão.

## Autenticidade das requisições

Toda entrega leva o cabeçalho **`x-webhook-signature`**: o HMAC-SHA256 do corpo
da requisição, exatamente como recebido, usando a **API Key da instância** como
chave. As requisições também levam o `User-Agent` `ZapperHub API`.

Para validar, recalcule a assinatura sobre o corpo bruto e compare:

```javascript
import { createHmac, timingSafeEqual } from 'node:crypto'

function isFromZapperHub(rawBody, signature, apiKey) {
  const expected = createHmac('sha256', apiKey).update(rawBody, 'utf8').digest('hex')
  return timingSafeEqual(Buffer.from(expected), Buffer.from(signature))
}
```

<Card title="IMPORTANTE">
A assinatura é a única maneira de garantir que as requisições que sua aplicação
recebe são oriundas do webhook da ZapperHub. Você é o responsável por executar
a validação da informação, bem como proteger sua aplicação com outras regras de 
segurança, como _rate limits_ e SSL. Nunca forneça a sua API Key, e sempre
que possível, faça uma rotação regular de seu valor.
</Card>

<Note>
A requisição de teste enviada no cadastro (`webhook.test`) é a única que **não**
leva assinatura — ela ocorre antes de o webhook existir.
</Note>

## Entrega

Cada entrega é feita por uma fila própria, com **5 tentativas** e intervalo
crescente entre elas, começando em 10 segundos. Cada tentativa tem **7 segundos**
de timeout: uma URL que demora mais do que isso para responder é tratada como
falha.

Sua aplicação deve responder com um status de sucesso o mais rápido possível, e
processar o conteúdo depois — não deixe a resposta esperando pelo seu
processamento.

O resultado de cada tentativa fica registrado em um recibo de entrega, com o
horário e o erro quando houver. Consulte por
`GET /{instanceId}/webhook-receipts` ou em **Ver recibos de entrega**, no
[Log de mensagens](/painel/log-de-mensagens).

<Card title="INFORMAÇÃO">
Os arquivos recebidos pelos Webhooks da ZapperHub ficam armazenados em nossos
servidores pelo prazo de 7 dias.
</Card>

## Eventos da própria sessão conectada

Por padrão, o webhook da ZapperHub trará também as mensagens enviadas pela própria 
sessão conectada. Isso ocorre porque trabalhamos com sistema de fila obrigatória,
de modo que após o envio da mensagem, não é possível ter o ID da mensagem, apenas
o jobId da fila.

Assim, as mensagens do webhook que tiverem o campo `jobId` referem-se a mensagens
disparadas pela ZapperHub, de modo que outras mensagens disparadas por outros
dispositivos não terão esse campo no webhook.

## Estrutura do payload

Os eventos de mensagem compartilham a mesma estrutura. O que muda de um tipo para
outro é o conteúdo do objeto `message`.

| Campo | Conteúdo |
| --- | --- |
| `type` | O evento, um dos listados acima |
| `instanceId` | Id da instância que gerou o evento |
| `chatId` | Id da conversa onde a mensagem ocorreu |
| `key.remoteJid` | JID da conversa — o contato, ou o grupo |
| `key.fromMe` | `true` quando a mensagem partiu da conta conectada |
| `key.id` | Id da mensagem no WhatsApp |
| `key.senderPn` / `key.senderLid` | Número e LID de quem enviou, em conversa individual |
| `key.participantPn` / `key.participantLid` | Número e LID de quem enviou, em grupo |
| `messageTimestamp` | Momento da mensagem, em segundos |
| `pushName` | Nome de exibição de quem enviou |
| `message` | O conteúdo, no formato do tipo da mensagem |
| `mediaUrl` | URL do arquivo já processado, nas mensagens de mídia |
| `jobId` | Id do job na fila, presente nas mensagens enviadas pela API |
| `trackId` / `trackSource` | Os valores informados no envio. Em mensagens recebidas, `trackSource` é `whatsapp` |

Em conexão oficial (Cloud API), os eventos carregam também o corpo original
enviado pela Meta, nos campos `object` e `entry`.

## Exemplos de payload

A seguir, iremos listar os exemplos de payload dos webhooks da ZapperHub, para 
os diferentes eventos.

### Teste do webhook

Tipo: `webhook.test`

Enviado uma única vez, no momento do cadastro, para verificar se a URL aceita
requisições `POST`.

```json
{
  "type": "webhook.test",
  "instanceId": "inst_01hxyz1234567890",
  "message": "If you see this message, your webhook is working correctly."
}
```

### Atualização da conexão

Tipo: `connection.update`

Disparado quando a instância conecta (`open`) ou é desconectada (`close`). O
campo `reason` aparece nas desconexões com causa conhecida — por exemplo, uma
conta removida na Meta ou um token do Instagram expirado.

```json
{
  "type": "connection.update",
  "instanceId": "inst_01hxyz1234567890",
  "connection": "close",
  "reason": "token_expired"
}
```

**Reação** (Cloud API e Instagram)

No Instagram, o evento chega com `trackSource: "instagram"`, o `key.id` é composto
(`ig-reaction:<mid>:<remetente>:<timestamp>`) e a retirada vem com `removed: true`,
como abaixo; o resto do formato é o mesmo.

Quando o contato reage a uma mensagem — ou o número reage pelo aparelho, no modo
de coexistência —, chega um `messages.upsert` com `reactionMessage`. O `key.id`
do evento é o da **própria reação**; a mensagem reagida está em
`reactionMessage.key.id`.

```json
{
  "type": "messages.upsert",
  "instanceId": "inst_01hxyz1234567890",
  "chatId": "5512912345678@s.whatsapp.net",
  "key": {
    "remoteJid": "5512912345678@s.whatsapp.net",
    "fromMe": false,
    "id": "wamid.HBgLNTUxMjkxMjM0NTY3OBUCABIYFjNFQjA",
    "senderPn": "5512912345678@s.whatsapp.net"
  },
  "messageTimestamp": 1744398716,
  "pushName": "John Doe",
  "broadcast": false,
  "message": {
    "reactionMessage": {
      "key": {
        "remoteJid": "5512912345678@s.whatsapp.net",
        "fromMe": true,
        "id": "3AB16AB78CD9012E89A0"
      },
      "text": "👍",
      "senderTimestampMs": 1744398716000
    }
  },
  "removed": false,
  "trackSource": "whatsapp"
}
```

- `reactionMessage.text` é o emoji. Quando o contato **retira** a reação, `text`
  vem vazio (`""`) e `removed` vem `true`.
- `reactionMessage.key.fromMe` indica de quem é a mensagem reagida: `true` quando
  o contato reagiu a uma mensagem da empresa, `false` quando o número reagiu, pelo
  aparelho, a uma mensagem do contato.
- Uma segunda reação à mesma mensagem é um evento novo, com outro `key.id`.
- Para reagir, use [`POST /{instanceId}/messages/react`](/functions/sending-messages#reagir-a-uma-mensagem).

### Outros tipos de mensagem recebidos

Tipo: `messages.upsert`

Além de texto, mídia, localização, contato e resposta de botão ou lista, a conexão
oficial (Cloud API) entrega os tipos abaixo. Todos chegam no mesmo envelope das
demais mensagens recebidas (`chatId`, `key`, `messageTimestamp`, `pushName`) e
aparecem em `GET /{instanceId}/messages` com o tipo correspondente. Nenhuma
mensagem é descartada: um tipo que a ZapperHub ainda não conhece chega como
`unknownMessage`.

| Conteúdo em `message` | Quando chega | Campos |
| --- | --- | --- |
| `flowResponseMessage` | O contato responde a um Flow | `name`, `body`, `responseJson` e `contextInfo.stanzaId` (o Flow respondido) |
| `callPermissionReplyMessage` | O contato responde ao pedido de permissão de ligação | `response` (`accept` ou `reject`), `expiresAt`, `permanent`, `source` e `contextInfo.stanzaId` |
| `systemMessage` | A Meta avisa de uma mudança na conversa, como a troca de número do contato | `type` (por exemplo `user_changed_number` ou `user_changed_user_id`) e `body` |
| `orderMessage` | O contato envia um pedido do catálogo | `catalogId`, `text` e `items[]` com `productRetailerId`, `quantity`, `itemPrice` e `currency` |
| `unsupportedMessage` | A Meta não repassa o tipo (poll, edição fora da coexistência, etc.) | `type` (o tipo informado pela Meta, como `edit`) e `error` (`code`, `title`, `details`) |
| `unknownMessage` | Qualquer tipo sem tratamento próprio | `type` (o tipo cru da Meta) e `raw` (a mensagem original) |

```json
{
  "type": "messages.upsert",
  "instanceId": "inst_01hxyz1234567890",
  "chatId": "5512912345678@s.whatsapp.net",
  "key": {
    "remoteJid": "5512912345678@s.whatsapp.net",
    "fromMe": false,
    "id": "wamid.HBgNNTUxMjkxMjM0NTY3OBUC",
    "senderPn": "5512912345678@s.whatsapp.net"

      }

```

- `flowResponseMessage.responseJson` é o objeto que o Flow devolveu. Se a Meta
  entregar um texto que não é JSON válido, ele vai como texto, sem perder a
  resposta.
- `callPermissionReplyMessage.expiresAt` é a data de validade da permissão em
  formato ISO 8601, e só vem em permissão temporária. `permanent` é `true` quando
  o contato aceitou de forma permanente.
- `systemMessage` informa o fato; a ZapperHub também atualiza o vínculo do
  contato quando se trata de troca de número ou de BSUID — veja
  [Identidade do contato](#identidade-do-contato-telefone-bsuid-e-username).
- Uma mensagem `unsupported` continua gerando também o `messages.error` com o
  código **131051**, como antes. A novidade é a mensagem em si chegar como
  `messages.upsert`.
- `unknownMessage.raw` leva a mensagem original da Meta, para que você trate o
  tipo novo sem esperar uma atualização da ZapperHub.

### Identidade do contato: telefone, BSUID e username

A Meta passou a identificar os contatos por um **BSUID** (`BR.13491208655302741918`)
e, quando o contato adota um **username**, pode deixar de informar o telefone. A
ZapperHub guarda o vínculo entre os três, **por empresa (WABA) e por dono**: todas
as suas instâncias na mesma WABA compartilham o vínculo, e ele nunca é visto por
outro dono, mesmo que ele use a mesma WABA.

**Como a conversa é identificada.** O `key.remoteJid` (e o `chatId`) de uma mensagem
segue sempre esta ordem:

1. o **telefone**, quando a Meta o informa no evento;
2. o telefone **já conhecido** para aquele BSUID;
3. o próprio **BSUID** (por exemplo, `BR.13491208655302741918`), quando o telefone
   ainda é desconhecido.

O `key.bsuid` e o `username` acompanham a mensagem sempre que são conhecidos — nas
mensagens recebidas, nos **ecos** de mensagens enviadas pelo aparelho e nos
[status de entrega](#estado-de-entrega-da-mensagem).

Tipo: `contacts.identity`

Quando o vínculo muda, a ZapperHub publica este evento em cada instância do mesmo
dono na WABA. É por ele que você junta duas conversas que eram do mesmo contato.

```json
{
  "type": "contacts.identity",
  "instanceId": "inst_01hxyz1234567890",
  "reason": "phone_discovered",
  "previous": { "phone": null, "bsuid": "BR.13491208655302741918", "username": "fulano" },
  "current": { "phone": "5512912345678", "bsuid": "BR.13491208655302741918", "username": "fulano" },
  "chatId": {
    "previous": "BR.13491208655302741918",
    "current": "5512912345678@s.whatsapp.net"
  },
  "timestamp": 1760000000
}
```

| `reason` | O que aconteceu |
| --- | --- |
| `phone_discovered` | Um contato que só tinha BSUID teve o telefone revelado |
| `phone_changed` | O contato trocou de número |
| `bsuid_changed` | O contato mudou de BSUID |
| `link_removed` | O telefone passou a pertencer a outro BSUID e deixou este vínculo |

- Use `chatId.previous` e `chatId.current` para migrar o histórico da conversa
  antiga para a nova.
- Uma entrega repetida da Meta não republica o evento.
- A primeira vez que a ZapperHub vê um contato **não** gera evento: só mudanças.
- A assinatura é **opt-in**: só recebe quem incluir `contacts.identity` em
  `subscriptions`.

### Opt-out de marketing

Tipo: `contacts.preference`

Quando um contato pede para **parar** (ou volta a **aceitar**) mensagens de
marketing — pela Meta, ou à mão pela
[API de contatos](/functions/contacts#opt-out-de-marketing) —, a ZapperHub publica
este evento em **todas as instâncias do mesmo dono na mesma WABA**: a escolha vale
para a empresa toda.

```json
{
  "type": "contacts.preference",
  "instanceId": "inst_01hxyz1234567890",
  "contact": { "phone": "5512912345678", "bsuid": "BR.13491208655302741918" },
  "category": "marketing_messages",
  "status": "opted_out",
  "source": "meta",
  "timestamp": 1731705721
}
```

- `status` é `opted_out` (não recebe marketing) ou `opted_in` (voltou a aceitar).
- `source` é `meta` (o contato pediu) ou `manual` (o integrador marcou pela API).
- `contact.phone` e `contact.bsuid` trazem o que a ZapperHub conhece do contato;
  qualquer um pode ser `null`.
- Entre a escolha da Meta e a manual vale a **mais recente**.
- A mesma escolha repetida não gera um segundo evento.
- Com `opted_out`, templates de **marketing** para o contato são recusados com
  `MARKETING_OPT_OUT`; utilidade e autenticação seguem.
- A assinatura é **opt-in**: só recebe quem incluir `contacts.preference` em
  `subscriptions`.

### Mensagem editada ou apagada

Tipo: `messages.update`

Quando o contato **edita** ou **apaga** uma mensagem — ou quando o próprio número
faz isso pelo aparelho —, a ZapperHub avisa com este evento. Ele aponta para a
mensagem **original**: `key.id` é o id dela, o mesmo que você recebeu antes em
`messages.upsert`. O id do evento de edição ou remoção vem em `eventId`.

```json
{
  "type": "messages.update",
  "instanceId": "inst_01hxyz1234567890",
  "chatId": "5512912345678@s.whatsapp.net",
  "key": {
    "remoteJid": "5512912345678@s.whatsapp.net",
    "fromMe": false,
    "id": "wamid.HBgLNTUxMjkxMjM0NTY3OBUCABIYFjNFQjA"
  },
  "update": {
    "kind": "edited",
    "message": {
      "extendedTextMessage": { "text": "Texto corrigido" }
    }
  },
  "eventId": "wamid.HBgLNTUxMjkxMjM0NTY3OBUCABIYFjNGQzE",
  "timestamp": 1749854575
}
```

Na remoção, `update` vem só com o tipo:

```json
{ "update": { "kind": "deleted" } }
```

- `update.kind` é `edited` ou `deleted`.
- Na edição, `update.message` traz o **texto** novo (`extendedTextMessage`) ou a
  **legenda** nova (`imageMessage`, `videoMessage` ou `documentMessage`, com
  `caption`). A mídia em si não é reenviada, porque não muda numa edição de
  legenda. Se a Meta não informar o conteúdo novo, `update.message` é omitido.
- A assinatura é **opt-in**: só recebe quem incluir `messages.update` em
  `subscriptions`. Quem assina apenas `messages.upsert` continua recebendo
  exatamente o que recebia.
- A Meta só envia estes eventos para números em **coexistência** com o app do
  WhatsApp Business. A edição vale até **15 minutos** depois do envio, e a remoção
  até **2 dias**.
- A mesma edição ou remoção entregue duas vezes pela Meta gera um único evento.

<Card title="ATENÇÃO">
A Meta entrega as **edições** como mensagem de tipo não suportado, e não no
formato próprio de edição. Por isso a edição chega como `messages.upsert` com
[`unsupportedMessage`](#outros-tipos-de-mensagem-recebidos) de `type` `edit`, sem
o texto novo, e não como `messages.update`. A **remoção** gera `messages.update`
normalmente.
</Card>

### Escolha de opção em mensagem de lista

Tipo: `messages.upsert`

Disparado quando o contato seleciona uma das opções da lista. O formato é o mesmo
em instância oficial (Cloud API) e não oficial:

- `message.listResponseMessage.selectedButtonId`: o `rowId` **exato** da opção
  escolhida, como você o definiu no envio
- `message.listResponseMessage.selectedDisplayText`: o texto exibido da opção
- `message.listResponseMessage.contextInfo.stanzaId`: o id da mensagem de lista
  original, útil para saber a qual menu a resposta se refere

```json
{
  "type": "messages.upsert",
  "instanceId": "inst_01hxyz1234567890",
  "chatId": "5512912345678@s.whatsapp.net",
  "key": {
    "remoteJid": "5512912345678@s.whatsapp.net",
    "fromMe": false,
    "id": "4D2AAEC025A74710866EF732A614AABA",
    "senderPn": "5512912345678@s.whatsapp.net"
  },
  "messageTimestamp": 1785312060,
  "pushName": "John Doe",
  "broadcast": false,
  "message": {
    "listResponseMessage": {
      "selectedButtonId": "cafe-01",
      "selectedDisplayText": "Café",
      "contextInfo": {
        "stanzaId": "3AB16AB78CD9012E89A0",
        "participant": "5512912345678@s.whatsapp.net"
      }
    }
  },
  "trackSource": "whatsapp"
}
```

<Card title="INFORMAÇÃO">
Em instâncias não oficiais, o bloco `listResponseMessage` traz **também** os
campos nativos do provedor (`title`, `description`, `listType`,
`singleSelectReply.selectedRowID`). A diferença é apenas aditiva: uma integração
que leia somente `selectedButtonId` e `selectedDisplayText` funciona sem
alteração nos dois canais.
</Card>

A resposta a uma mensagem com **botões** chega da mesma forma, em
`message.buttonsResponseMessage`.

### Estado de entrega da mensagem

Tipo: `messages.status`

Disparado a cada mudança de estado de uma mensagem enviada, em instâncias
oficiais (Cloud API) e não oficiais (DEVICE). Na Cloud API, o campo `status`
acompanha os valores da Meta — `sent`, `delivered`, `read` e `failed` —, e
`error` só aparece nas falhas.

```json
{
  "type": "messages.status",
  "instanceId": "inst_01hxyz1234567890",
  "messageId": "wamid.HBgNNTUxMjkxMjM0NTY3OBUCABEYEjc0NjcyOTk2MEE1MEJDNTY2AA==",
  "recipientId": "5512912345678",
  "status": "delivered",
  "timestamp": 1785312030
}
```

#### Em conexão não oficial (DEVICE)

O evento chega com `status` `delivered` (dois checks) ou `read` (dois checks
azuis), uma vez por mensagem — quando o WhatsApp agrupa vários recibos, cada
mensagem do lote gera o seu evento. O `messageId` é o mesmo `key.id` recebido no
`messages.upsert` do envio.

```json
{
  "type": "messages.status",
  "instanceId": "inst_01hxyz1234567890",
  "messageId": "3AB16AB78CD9012E89A0",
  "recipientId": "5512912345678",
  "recipientPn": "5512912345678",
  "chatId": "5512912345678@s.whatsapp.net",
  "status": "read",
  "timestamp": 1785312030
}
```

- `chatId` é a conversa. Quando ela é identificada por LID, o evento traz
  `recipientLid` com o LID e, se a ZapperHub já conhece o vínculo,
  `recipientPn` com o telefone; sem o vínculo, `recipientId` carrega o LID.
- Não há `sent` nem `failed` em conexão não oficial: a confirmação de envio é a
  resposta da API, e a falha definitiva chega em `messages.error`.
- Recibos de **grupo** não são entregues.
- Se o contato desativou a confirmação de leitura nas configurações de
  privacidade do WhatsApp, o evento `read` não chega — só o `delivered`.
- Para avisar o WhatsApp de que **você** leu uma mensagem, use
  [Marcar como lida](/functions/sending-messages#marcar-como-lida).

#### Em conexão oficial (Cloud API)

Quando a ZapperHub conhece o BSUID ou o username do destinatário — porque a Meta
os informou no próprio status ou porque o contato já tinha escrito antes —, o
evento traz também `bsuid` e `username`. Se o destinatário não tem telefone
visível, `recipientId` carrega o BSUID.

### Falha no envio de mensagens

Tipo: `messages.error`

Como o envio é feito por fila, o `200` da API confirma o enfileiramento e não a
entrega. Quando as 5 tentativas automáticas de envio se esgotam, a ZapperHub
dispara este evento — nenhuma mensagem chegou ao destinatário. Uma falha
intermediária seguida de sucesso **não** dispara o evento.

Ele vale para **todos os tipos de mensagem** enviados pela API.

```json
{
  "type": "messages.error",
  "instanceId": "inst_01hxyz1234567890",
  "jobId": "42",
  "key": {
    "id": "job_42",
    "fromMe": true,
    "remoteJid": "5512912345678@s.whatsapp.net"
  },
  "error": {
    "code": 131000,
    "title": "Something went wrong",
    "message": "Message failed to send because of an unknown error.",
    "error_data": {
      "details": "connect ETIMEDOUT 10.0.0.1:443"
    },
    "href": "https://developers.facebook.com/docs/whatsapp/cloud-api/support/error-codes/"
  },
  "timestamp": 1753758000,
  "trackId": "pedido-8823",
  "trackSource": "crm"
}
```

- O bloco `error` segue o **formato de erro da Cloud API**, o mesmo que a Meta já
  usa nos erros que repassamos: uma integração escrita contra aquele formato lê
  este evento sem tratamento novo.
- `error.code` repassa o **código original da Meta** quando a falha veio da
  própria Cloud API (por exemplo, `131047` para janela de 24 horas expirada, ou
  `131026` para destinatário inalcançável). O código `131000` fica reservado ao
  que não tem código de provedor: instâncias não oficiais, timeout e falhas de
  rede.
- `error.error_data.details` traz o erro real do envio; `error.message` é a
  descrição estável do código.
- `error.localizedMessage` traz a explicação **em português** para os códigos da
  Meta que a ZapperHub conhece (por exemplo, `131047`: "Passaram mais de 24 horas
  desde a última mensagem do contato. Envie um template de mensagem.").
  O campo só aparece quando há tradução; os demais campos do bloco `error` não
  mudam.
- `key.id` é derivado do job (`job_<jobId>`), e não do provedor — o envio nunca
  chegou a produzir um id de mensagem. É também o que distingue uma falha nascida
  na nossa fila de um erro reportado pela Meta.
- `trackId` e `trackSource` são os mesmos informados no envio, o que permite
  relacionar a falha ao registro da sua aplicação.

### Mudança de participantes em grupo

Tipo: `group-participants.update`

Disparado em instâncias não oficiais quando alguém entra, sai, é promovido a
administrador ou rebaixado. Os campos `join`, `leave`, `promote` e `demote`
trazem os participantes afetados — **apenas o correspondente ao que aconteceu
vem preenchido**, os demais são omitidos.

```json
{
  "type": "group-participants.update",
  "groupId": "120363012345678901@g.us",
  "join": ["5512912345678@s.whatsapp.net"],
  "timestamp": "2026-07-29T12:00:00Z"
}
```

#### Valores de `event` por origem

| `event` | Conexão oficial (Cloud API) | Conexão não oficial (device) |
| ------- | --------------------------- | ---------------------------- |
| `connect` | Chamada do usuário chegando ao número. Sem `status` | Chamada chegando ao número. Sem `status` |
| `status` | Progresso da chamada: `RINGING`, `ACCEPTED` ou `REJECTED` | Chamada atendida: `ACCEPTED` |
| `terminate` | Encerramento: `COMPLETED` ou `FAILED` | Encerramento: `REJECTED`, `MISSED`, `ACCEPTED`, `COMPLETED`, `FAILED` — ou omitido |
| `error` | Falha reportada pela Meta | Não ocorre |

`MISSED` — chamada que tocou até expirar — é **exclusivo da conexão não
oficial**. A conexão oficial não publica esse desfecho.

Em conexão não oficial, `status` **ausente** em um `terminate` significa que o
motivo não é previsto pela plataforma. Use `reason`, que vem sempre.

#### Diferenças entre as duas origens

| | Conexão oficial (Cloud API) | Conexão não oficial (device) |
| --- | --- | --- |
| Campos exclusivos | `startTime`, `endTime`, `duration`, `bizOpaqueCallbackData`, `username` | `reason`, `groupId`, `key.senderLid` / `key.participantLid` |
| `key.addressingMode` | Sempre `pn` | `pn` ou `lid`, conforme o contato |
| Chamada de grupo | Não se aplica | `groupId` e `key.participantPn` |
| Ocorrência bruta | Espalhada no payload (`object` e `entry`) | Em `rawEvent` |

Campo sem valor na origem é **omitido** — nunca enviado como `null` ou string
vazia.

<Card title="IMPORTANTE">
A assinatura de `calls.update` é **opt-in**: só recebe quem incluir a string
explicitamente em `subscriptions`. Nenhuma assinatura existente é alterada
automaticamente.

Assine pelo seletor de eventos do painel, ou pela API com
`PUT /{instanceId}/webhooks/{webhookId}`.

Chamada **não** é mensagem: o evento **não** é encaminhado ao Chatwoot e **não**
é gravado no histórico de conversas.
</Card>

<Card title="CONEXÃO OFICIAL: A ASSINATURA ATIVA AS CHAMADAS NO NÚMERO">
Em conexão oficial, a Meta só emite eventos de chamada — e só mostra o botão de
ligação ao usuário — em número com o recurso de chamadas **habilitado**. Um
número Cloud API nasce com ele desligado.

Por isso, assinar `calls.update` faz a plataforma habilitar o recurso no seu
número antes de salvar o webhook. Você não precisa fazer nada na Meta. Se o
recurso já estiver habilitado, nada é alterado — suas preferências de horário de
atendimento, visibilidade do botão e SIP permanecem intactas.

Quando a habilitação não é possível, **o webhook não é salvo** e a resposta diz
qual é o caso:

| Resposta | `code` | O que fazer |
|---|---|---|
| `422` | `CALLING_API_UNAVAILABLE` | O número não se qualifica para a Calling API. Salve novamente **sem** `calls.update` — repetir o mesmo pedido falhará de novo |
| `503` | `PROVIDER_UNAVAILABLE` | Não foi possível falar com a Meta agora. Repita o mesmo pedido em instantes |

A recusa vale para o pedido inteiro: nome, URL e as demais assinaturas enviadas
junto também não são gravados.

Os pré-requisitos da Calling API são da Meta, não da plataforma: número Cloud API
**nativo** (coexistência não se qualifica), limite diário de pelo menos 2.000
destinatários únicos e campo `calls` assinado na configuração do aplicativo.

Em conexão **não oficial** nada disso se aplica — chamadas chegam sem
configuração e a assinatura não passa por essa verificação.
</Card>

<Card title="ATENÇÃO">
Em conexão não oficial, chamadas recebidas enquanto a instância estava
**desconectada não são recuperadas**. O WhatsApp não as reentrega quando a
sessão volta, e a plataforma não as compensa — o evento simplesmente não existiu
para a instância.
</Card>

### Gravação disponível

Tipo: `calls.update`, com `event: "recording"`

Disparado quando a gravação de uma chamada fica pronta — **em conexão não
oficial**, e apenas para chamadas em que a gravação foi solicitada. É um evento
**separado** do encerramento: aquele sai assim que a chamada termina, sem esperar
o processamento da gravação. Correlacione os dois pelo `callId`.

```json
{
  "type": "calls.update",
  "instanceId": "inst_01hxyz1234567890",
  "chatId": "5511999999999@s.whatsapp.net",
  "key": {
    "remoteJid": "5511999999999@s.whatsapp.net",
    "fromMe": false,
    "id": "3EB0C767D26B8CE6A1B4",
    "addressingMode": "pn",
    "senderPn": "5511999999999@s.whatsapp.net"
  },
  "callId": "3EB0C767D26B8CE6A1B4",
  "event": "recording",
  "direction": "USER_INITIATED",
  "timestamp": 1787072580,
  "trackSource": "whatsapp",
  "recording": {
    "status": "AVAILABLE",
    "url": "https://storage.zapperhub.com/...&X-Amz-Expires=3600",
    "expiresAt": "2026-09-04T19:23:47.000Z",
    "durationSeconds": 216,
    "truncated": false
  }
}
```

O arquivo contém **os dois lados** da conversa. O endereço vem pronto e assinado:
não é preciso autenticar para baixar, nem informar um destino próprio.

| Campo | Descrição |
| --- | --- |
| `recording.status` | `AVAILABLE` ou `UNAVAILABLE` |
| `recording.url` | Endereço de download, válido por 1 hora |
| `recording.expiresAt` | Quando **este** endereço expira |
| `recording.durationSeconds` | Duração do áudio gravado |
| `recording.truncated` | `true` quando a gravação foi cortada no limite de 1 hora |

O endereço expirar não é problema: consulte
`GET /{instanceId}/calls/{callId}` para obter um novo, enquanto a gravação
existir.

Quando a gravação fica definitivamente indisponível, o mesmo evento traz o
motivo — e o evento de encerramento, já entregue, **não** é reenviado:

```json
{
  "event": "recording",
  "callId": "3EB0C767D26B8CE6A1B4",
  "recording": { "status": "UNAVAILABLE", "reason": "STORAGE_FAILED" }
}
```

<Card title="A GRAVAÇÃO EXPIRA EM 7 DIAS">
Passados 7 dias do encerramento, o arquivo é descartado em definitivo. O
**registro** da chamada continua consultável por 90 dias e informa que a gravação
já não existe, em vez de devolver um endereço que não resolve.

Baixe e guarde o arquivo do seu lado se precisar dele por mais tempo.
</Card>

Consulte [Chamadas](/functions/calls) para originar, atender, gravar e encerrar
chamadas por API.

### Comentário recebido no Instagram

Tipo: `comments.upsert`

Disparado em instâncias do Instagram quando um comentário é recebido em um post
da conta. A estrutura é a mesma de `messages.upsert`, acrescida do bloco
`comment`.

```json
{
  "type": "comments.upsert",
  "key": {
    "id": "17984523698451234",
    "fromMe": false,
    "remoteJid": "17841400000000000",
    "senderId": "17841400000000000",
    "recipientId": "17841411111111111"
  },
  "messageTimestamp": 1785312000,
  "pushName": "john.doe",
  "broadcast": false,
  "message": {
    "extendedTextMessage": {
      "text": "Vocês entregam em São Paulo?"
    }
  },
  "comment": {
    "id": "17984523698451234",
    "text": "Vocês entregam em São Paulo?",
    "postId": "17895695668004550",
    "parentCommentId": null,
    "from": {
      "id": "17841400000000000",
      "username": "john.doe"
    },
    "timestamp": 1785312000
  },
  "trackSource": "instagram"
}
```

<Card title="ATENÇÃO">
Diferente de uma mensagem, o comentário é **público**: qualquer visitante do
perfil o vê. Ele não é encaminhado ao Chatwoot e **não é deduplicado** — a Meta
pode reentregar a mesma notificação. Trate `comment.id` como chave de
idempotência e ignore entregas repetidas do mesmo id.
</Card>

Para responder em privado o autor do comentário, use `commentId` em
`POST /{instanceId}/messages/text`.

### Token do Instagram expirado

Tipo: `token.expired`

Disparado quando o token de acesso do Instagram expirou ou foi revogado. É um
evento terminal: a instância é desconectada e **exige nova autorização**. Um
`connection.update` com `connection: "close"` acompanha o evento.

```json
{
  "type": "token.expired",
  "instanceId": "inst_01hxyz1234567890",
  "reason": "token_expired",
  "expiredAt": "2026-07-29T03:00:00.000Z",
  "requiresReauth": true
}
```

O campo `reason` é `token_expired` ou `token_revoked`.

### Falha ao renovar o token do Instagram

Tipo: `token.refresh.failed`

Disparado a cada tentativa de renovação que falha por causa temporária — uma
instabilidade da Meta, por exemplo. A renovação continua sendo tentada, e
`failureCount` acumula: use-o para escalonar o alerta interno antes que a falha
se torne terminal.

```json
{
  "type": "token.refresh.failed",
  "instanceId": "inst_01hxyz1234567890",
  "origin": "automatic",
  "failureCount": 3,
  "reason": "temporary",
  "errorCode": 190,
  "expiresAt": "2026-08-15T03:00:00.000Z"
}
```

`origin` indica se a tentativa partiu da rotina automática (`automatic`) ou da
rota de renovação manual (`manual`).

<Card title="IMPORTANTE">
Sem assinar `token.refresh.failed` e `token.expired`, você só percebe o problema
quando ele já é terminal, pelo `connection.update` — e não recebe aviso algum
durante a janela de retentativa.
</Card>
